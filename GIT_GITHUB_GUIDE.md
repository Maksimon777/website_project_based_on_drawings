# Git + GitHub + VS Code: инструкция для команды «ЧЕРТЕЖИ»

Для Windows. Работаем на бесплатном GitHub Free: локальная разработка в VS Code, общий приватный репозиторий, задачи и проверка изменений в браузере. Банковская карта для этого сценария не нужна. Выбирайте Free, без подключения платных пробных подписок. [Тариф GitHub Free](https://github.com/pricing).

**Как читать файл:** откройте его в VS Code и нажмите **Ctrl+Shift+V** — появятся оформленные заголовки и таблицы. Чтобы видеть текст и предпросмотр рядом: **Ctrl+K**, отпустить клавиши, затем **V**.

## 1. Что устанавливать и кто что делает

| Инструмент | Для чего нужен |
|---|---|
| Git | Хранит историю изменений файлов на компьютере |
| VS Code | Редактор файлов со встроенными кнопками работы с Git |
| GitHub | Сайт, где команда хранит общую версию проекта и проверяет изменения |
| GitHub Issues | Карточки задач с описанием и исполнителем |
| GitHub Projects | Доска, на которой видно состояние задач |

**Каждому участнику:** установить Git и VS Code, зарегистрироваться на GitHub, принять приглашения и скачать репозиторий.

**Тим-лиду:** создать общий репозиторий и доску, пригласить участников, ставить задачи и принимать результат.

**Глебу:** помогать с техническими настройками и проверять изменения Матвея. Тим-лид проверяет соответствие результата задаче. Автор не принимает собственную работу единолично.

## 2. Регистрация на GitHub — каждому

1. Откройте [GitHub](https://github.com/) и нажмите **Sign up**.
2. Пройдите регистрацию, укажите собственный email и подтвердите его.
3. Используйте бесплатный аккаунт **Free**.
4. Сообщите тим-лиду свой **username** — имя пользователя GitHub.

Каждый работает под собственным аккаунтом. Если GitHub предложит настроить двухфакторную аутентификацию, завершите настройку и сохраните коды восстановления.

[Официальная инструкция регистрации](https://docs.github.com/en/account-and-profile/how-tos/account-management/creating-an-account-on-github).

## 3. Установка Git и VS Code — каждому

Если программы уже установлены, переходите к проверке Git ниже.

1. Установите [VS Code с официального сайта](https://code.visualstudio.com/), если его ещё нет.
2. Откройте [Git для Windows](https://git-scm.com/install/windows).
3. Для обычного компьютера Intel/AMD скачайте **Git for Windows/x64 Setup**. Для компьютера с процессором ARM — ARM64. Тип системы можно посмотреть в Windows: **Параметры → Система → О системе**.
4. Запустите установщик Git. Большинство настроек оставьте по умолчанию.
5. Если есть выбор редактора, выберите **Visual Studio Code**.
6. На шаге PATH выберите **Git from the command line and also from 3rd-party software**: это позволит VS Code находить Git.
7. Оставьте включённым **Git Credential Manager** — он помогает входить в GitHub через браузер.
8. Завершите установку и полностью перезапустите VS Code.

Git Credential Manager входит в Git for Windows. Для обычной работы по HTTPS используем вход через браузер. [Документация GitHub](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

### Проверка установки

В VS Code сверху выберите **Terminal → New Terminal / Терминал → Создать терминал**. Внизу появится область ввода. Введите команду и нажмите Enter:

```powershell
git --version
```

Ответ должен начинаться с `git version` и содержать номер версии.

### Настройка имени автора

Введите следующие команды по одной. Замените имя и email своими данными:

```powershell
git config --global user.name "Ваше имя"
git config --global user.email "your-email@example.com"
```

Эти данные обозначают автора изменений, а не служат паролем для входа. Используйте email, добавленный в GitHub. Для скрытия личного адреса можно взять адрес `noreply`, который GitHub показывает в **Settings → Emails**. `--global` означает настройку для всех репозиториев текущего пользователя Windows.

[Настройка Git](https://git-scm.com/book/en/v2/Getting-Started-First-Time-Git-Setup), [email автора на GitHub](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address).

## 4. Создание общего репозитория — тим-лиду

Репозиторий — это файлы проекта вместе с историей изменений. Для старта создаём один репозиторий в личном аккаунте тим-лида.

1. На GitHub нажмите **+ → New repository**.
2. Заполните настройки:

| Поле | Значение |
|---|---|
| Owner | Аккаунт тим-лида |
| Repository name | `chertezhi` |
| Description | Веб-сервис заказов на чертежи и учебные работы |
| Visibility | **Private** — доступ только приглашённым |
| Add README | Включить |
| Add .gitignore | Выбрать **Python** |
| License | Пока оставить без выбора |

3. Нажмите **Create repository**.
4. Проверьте имя основной ветки над списком файлов: используем **main**. Если она называется иначе, откройте список веток **View all branches** и переименуйте основную ветку в `main`.

Этот порядок подходит для нового проекта без существующей истории Git. Если код уже ведётся в другом репозитории, Глебу нужно перенести его с сохранением истории в пустой репозиторий, без отдельного создания README.

[Создание репозитория](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository).

### Пригласить Глеба и Матвея

1. В репозитории откройте **Settings → Collaborators**.
2. Нажмите **Add people**.
3. Найдите участника по его username и отправьте приглашение.
4. Участник должен принять приглашение, затем открыть репозиторий под своим аккаунтом.

GitHub Free позволяет приглашать участников в приватные репозитории бесплатно. [Приглашение участников](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository).

### Договорённость о main

В приватном репозитории GitHub Free защита веток с обязательным одобрением PR недоступна. Поэтому на старте команда соблюдает правила самостоятельно:

- Каждая задача выполняется в отдельной ветке от актуальной `main`.
- Изменения отправляются на проверку через Pull Request.
- В `main` работу объединяет тим-лид или назначенный им проверяющий после приёмки.

GitHub на этом тарифе не будет автоматически запрещать участникам обходить договорённость. [Доступность защиты веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## 5. Скачать проект в VS Code — каждому

Это называется **клонировать репозиторий**. Выполняется один раз на каждом компьютере.

1. Откройте репозиторий на GitHub.
2. Нажмите зелёную кнопку **Code → Local → HTTPS** и скопируйте адрес.
3. В VS Code нажмите **Ctrl+Shift+P** — откроется поиск команд редактора.
4. Найдите **Git: Clone**, вставьте адрес и нажмите Enter.
5. Выберите папку для проектов, например `Документы\Projects`. В ней появится папка `chertezhi`.
6. Если потребуется авторизация, завершите вход в GitHub через браузер под приглашённым аккаунтом.
7. Нажмите **Open / Открыть**. Подтвердите доверие к папке своего командного проекта, если редактор спросит.

Обычный пароль GitHub не используется как пароль Git при работе по HTTPS. Для этой инструкции достаточно браузерного входа через редактор или Git Credential Manager.

Не нажимайте **Initialize Repository** внутри уже клонированного проекта. [Клонирование в VS Code](https://code.visualstudio.com/docs/sourcecontrol/repos-remotes), [вход в GitHub](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

## 6. Как ставить задачи

В репозитории откройте **Issues → New issue**. Напишите конкретное название, например «Добавить MVP.md в репозиторий», и назначьте исполнителя через **Assignees**.

В описание каждой задачи включайте пять пунктов:

1. **Что сделать:** конкретное действие.
2. **Зачем:** какую пользу это даёт MVP.
3. **Входные данные:** файлы, требования и договорённости для начала работы.
4. **Ожидаемый результат:** что исполнитель сдаёт.
5. **Критерии готовности (DoD):** как проверить работу.

После создания у задачи появится номер, например **#12**. Этот номер используем в названии ветки и описании PR. Issue — это рабочая карточка; она может описывать новую функцию, документ или ошибку. [Работа с задачами](https://docs.github.com/en/get-started/start-your-journey/planning-your-work).

Задачи больше 1–2 дней разбивайте. В задачах Матвея добавляйте «Обучающий вектор»: конкретный раздел документации Django/PostgreSQL и небольшой пример по теме.

## 7. Доска задач — тим-лиду

1. Нажмите аватар на GitHub → **Your profile → Projects → New project**.
2. Выберите **Board** и название `ЧЕРТЕЖИ — MVP`, затем **Create project**.
3. В настройках доски проверьте видимость **Private**.
4. Используйте три значения поля **Status**:

| Колонка | Когда ставить |
|---|---|
| Todo | Работа ещё не начата |
| In Progress | Исполнитель работает или ожидает проверки PR |
| Done | Тим-лид принял результат; нужные изменения включены в main |

Названия колонок можно изменить. [Создание доски](https://docs.github.com/en/issues/planning-and-tracking-with-projects/creating-projects/creating-a-project).

**Доступ к доске выдаётся отдельно:** откройте её меню **… → Settings → Manage access**, пригласите Глеба и Матвея с ролью **Write**. Для просмотра карточек приватного репозитория им также нужен доступ к самому репозиторию из раздела 4. [Права на Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects).

Откройте созданную Issue и справа в **Projects** выберите эту доску. Если поле скрыто узким окном, разверните окно или откройте настройки карточки. Добавляйте на доску существующие Issues, чтобы у каждой задачи оставались номер, описание и обсуждение.

## 8. Как выполнять задачу в VS Code

### Создать ветку

1. Переведите карточку своей задачи в **In Progress**.
2. Откройте в VS Code папку клонированного проекта.
3. Нажмите **Ctrl+Shift+G** — раздел **Source Control / Управление версиями**. Перед переключением ветки сохраните незавершённую работу предыдущей задачи коммитом в её собственной ветке.
4. Нажмите название ветки внизу слева и выберите **main**.
5. Через **Ctrl+Shift+P → Git: Pull** получите последние изменения команды.
6. Через **Ctrl+Shift+P → Git: Create Branch** создайте ветку, например `task/12-add-mvp`.
7. Убедитесь, что внизу слева указана новая ветка, и только затем изменяйте файлы.

Число `12` здесь — пример: используйте номер своей Issue. Ветка отделяет работу над вашей задачей от принятой общей версии. [Ветки в VS Code](https://code.visualstudio.com/docs/sourcecontrol/branches-worktrees).

### Сохранить изменения и отправить их

1. Сохраните изменённые файлы.
2. Откройте **Source Control** и нажмите каждый изменённый файл, чтобы просмотреть различия.
3. Нажмите **+** возле нужных файлов: действие **Stage Changes** выбирает изменения для следующего коммита.
4. В поле сообщения напишите, что сделано, например `Добавлено описание MVP`.
5. Нажмите **Commit** — изменения сохранятся в локальной истории.
6. Для новой ветки нажмите **Publish Branch**, а для следующих отправок используйте **Ctrl+Shift+P → Git: Push**.

**Сохранить файл, сделать Commit и выполнить Push — три отдельных действия.** После Push изменения доступны команде на GitHub в вашей ветке. [Коммиты в VS Code](https://code.visualstudio.com/docs/sourcecontrol/staging-commits), [отправка изменений](https://code.visualstudio.com/docs/sourcecontrol/repos-remotes).

Перед первой отправкой кода Глеб проверяет `.gitignore`: в репозиторий не должны попадать `.env` с паролями, `.venv`, локальная БД и загруженные заказчиками файлы. Шаблон Python может потребовать дополнений под структуру проекта.

## 9. Проверка через Pull Request

**Pull Request (PR)** — запрос включить изменения вашей ветки в `main` после проверки.

### Исполнителю

1. После Push откройте репозиторий на GitHub.
2. Нажмите **Compare & pull request**. Если баннера нет: **Pull requests → New pull request**.
3. Проверьте направления: **base: main**, **compare: ваша ветка**.
4. Укажите понятное название и описание: что изменено, как проверено, что нужно проверить вручную.
5. Добавьте в описание `Closes #12`, заменив номер на свою Issue. После слияния в основную ветку эта задача закроется автоматически.
6. Выберите проверяющего в **Reviewers** и нажмите **Create pull request**.
7. Исправляйте замечания в той же ветке. Новый Commit и Push обновляют существующий PR.

[Создание PR](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-a-pull-request), [связь PR с задачей](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).

### Проверяющему и тим-лиду

1. Откройте PR → **Files changed** и просмотрите изменения.
2. Проверьте результат по DoD задачи.
3. Нажмите **Review changes**: **Request changes**, если нужны исправления, или **Approve**, если работа принята.
4. После проверки ответственный нажимает **Merge pull request → Confirm merge**. Одно нажатие Approve ещё не объединяет изменения.
5. После слияния можно нажать **Delete branch** для удаления завершённой ветки на GitHub.
6. Проверьте, что Issue закрыта и карточка на доске имеет статус **Done**. Если автоматизация доски не изменила статус, измените его вручную.

[Проверка PR](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request), [слияние PR](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request).

После этого участники переключаются в `main` и выполняют **Git: Pull**. Следующую задачу начинают с новой ветки.

## 10. Первая практическая задача

**Исполнитель: тим-лид. Проверяющий: Глеб.**

1. **Что сделать:** добавить подготовленный `MVP.md` в корень общего репозитория через отдельную ветку и PR.
2. **Зачем:** дать команде общую точку отсчёта по MVP и проверить весь процесс совместной работы.
3. **Входные данные:** готовый `MVP.md`, доступ к репозиторию и установленный Git.
4. **Ожидаемый результат:** принятый PR с документом в `main`.
5. **Критерии готовности (DoD):** документ читается на GitHub; Глеб проверил PR; Issue закрыта; Матвей получил файл через Pull.

Скопируйте готовый файл в папку клонированного репозитория после создания ветки, затем пройдите разделы 8–9. Только перенос файла на компьютер не добавляет его в общий репозиторий.

## 11. Если что-то не работает

| Ситуация | Что сделать |
|---|---|
| `git` не распознаётся | Полностью перезапустить VS Code; если не помогло, проверить установку Git и настройку PATH |
| Приватный репозиторий показывает 404 | Проверить аккаунт и принятие приглашения: GitHub может скрывать существование недоступного репозитория |
| Репозиторий виден, доска нет | Проверить отдельное приглашение в Projects и права на доску |
| Git просит имя и email | Выполнить настройку автора из раздела 3 |
| Коллеги не видят изменения | Выполнить Push и проверить выбранную ветку на GitHub |
| Не получается создать PR | Проверить, что изменения отправлены, а base и compare — разные ветки |
| В PR конфликт | Обратиться к Глебу: нужно объединить изменения в рабочей ветке, проверить результат и повторить Push |
| Markdown выглядит как обычный текст | Нажать Ctrl+Shift+V для предпросмотра |

При конфликте не выбирайте вслепую «принять все мои» или «принять все входящие»: обе стороны могут содержать нужные изменения.

## 12. Памятка на каждый день

| Действие | Значение |
|---|---|
| Clone | Впервые скачать репозиторий и его историю |
| Pull | Получить и включить изменения с сервера в текущую ветку |
| Branch | Отдельная линия работы над задачей |
| Stage | Выбрать изменения для коммита |
| Commit | Сохранить выбранные изменения в локальной истории |
| Push | Отправить коммиты на GitHub |
| Pull Request | Передать работу на проверку |
| Approve | Одобрить изменения |
| Merge | Объединить изменения с основной веткой |

**Issue → обновить main → создать ветку → изменить файлы → Commit → Push → PR → проверка → Merge → Done.**

Инструкция подготовлена 24 сентября 2026 года. Названия кнопок могут немного отличаться в зависимости от языка и обновлений интерфейса. Она описывает настройку и работу команды; установка Django, запуск сайта и его публикация выполняются отдельно.
